Blitzlog · Auth lifecycle

GitHub App installation token, from launch to self-perpetuating chain

Four lifecycle layers. The launch-time mint is a one-shot; the chain self-perpetuates every 50 min via EventBridge Scheduler; the host's poll loop runs every 5 min to keep the bind-mounted credentials in sync. Container restarts are not required.

1 Launch-time mint one-shot · runs once at webhook time
GitHub

Issue labeled

User adds a trigger label to an issue. The webhook fires the Lambda with the issue payload (repo, issue number, sender).

AWS Lambda

handler.py

Verifies the webhook HMAC, then in launch_ec2_spot_instance:

  • get_github_app_token(repo) mints a fresh installation token
  • ssm.put_parameter writes it to /blitzlog/<env>/ephemeral/gh/<owner>/<repo>/<issue>
  • schedule_next_refresh(iteration=0) queues the first chain event
SSM Parameter Store

SSM parameter

Path: /blitzlog/<env>/ephemeral/gh/<owner>/<repo>/<issue>

Type: SecureString. Lifetime: 1 h (GitHub caps installation tokens at 1 h regardless of requested expires_at).

Version: starts at 1, increments on every chain mint.

2 EC2 boot · single read runs once per instance lifetime
EC2 host · user-data

User-data heredoc

The Lambda's script_header() rendered a shell heredoc that the EC2 user-data downloads from S3. It exports GITHUB_TOKEN_SSM_PARAM (the SSM path) so the watchdog can read it.

EC2 host · watchdog.sh

Single read + write

At line 109, watchdog.sh reads SSM once:

  • aws ssm get-parameter --with-decryption
  • Writes the token to /root/.git-credentials.d/github (git) and /root/gh-config/<instance>/hosts.yml (gh CLI)
  • Forks the poll loop (Layer 4) into a subshell
Container

Bind-mounted credentials

Both files are bind-mounted into the container:

  • -v /root/.git-credentials.d:/root/.git-credentials.d
  • -v /root/gh-config/<instance>:/root/.config/gh

git and gh read these on every invocation. No restart needed.

3 Chain self-perpetuation 50-min cycle · up to 10 hops
EventBridge Scheduler

Fires one-time

Each chain event is refresh-issue-N-iter-K (K = 0…9), FlexibleTimeWindow.mode = "OFF" (fire exactly once, no slack), scheduled at(<ISO 8601>) in the per-env group blitzlog-<env>-token-refresh.

AWS Lambda · _handle_refresh

Mint + write + reschedule

Same path as the launch-mint, in 3 lines:

  • get_github_app_token(repo)
  • ssm.put_parameter(... overwrite=True) (Version++)
  • schedule_next_refresh(iteration=K+1) if K < 9

If the EC2 instance is already gone, the schedule still fires; the SSM put succeeds; the next hop is queued. No-op against a missing INSTANCE_ID.

SSM (Version+1)

New token, same path

Same SSM parameter, Version incremented. New iat = fire-time, new exp = +1 h. The next schedule_next_refresh queues the following 50-min event, so the chain keeps itself alive for up to ~8.3 h per instance (10 hops).

4 Continuous refresh 5-min poll · runs for the full instance lifetime
EC2 host · blitzlog_token_poll.sh

Poll loop

Forked by the watchdog at line 234. While the watchdog runs, this subshell wakes every 5 min, reads the SSM parameter, and compares to its in-memory last:

  • Same → no-op, no log
  • Different → overwrites bind mount + logs "Token change detected"
  • Empty read → preserves last, no log (false-positive guard)
SSM

Same path, new value

The poll loop reads the same SSM parameter the chain writes to. If Version has advanced since the last read, the bind mount is rewritten in place.

Container

In-place rewrite, no restart

The bind-mounted files are atomically replaced. The next git push / gh call inside the container re-reads the file via the credential helper and uses the new token. No in-container code change, no signal, no restart.

IAM footnote — three grants keep the chain alive

Each layer of this diagram is gated on an IAM grant; if any of them is missing, the chain dies and the bind mount holds the launch-mint token until the instance shuts down. The PR #146 / #154 history is largely about the IAM grants that were missing at launch and how they were added.

Deploy role blitzlog-deploy-role
  • scheduler:GetScheduleGroup + :CreateScheduleGroup + :UpdateScheduleGroup + :DeleteScheduleGroup
  • scheduler:ListScheduleGroups
  • scheduler:ListTagsForResource + :TagResource + :UntagResource
  • Resource: schedule-group/blitzlog-*-token-refresh
  • Where: infra/bootstrap/deploy-role.tf · Sid SchedulerScheduleGroupManagement (PR #154 commit a8115ff)
Lambda role blitzlog-<env>-lambda-role
  • scheduler:CreateSchedule + :DeleteSchedule
  • ssm:PutParameter on the ephemeral namespace
  • Resource: schedule/<group>/*
  • Where: infra/modules/core/iam.tf · pre-existing from PR #146
Lambda role · iam:PassRole for the scheduler role
  • iam:PassRole on blitzlog-<env>-scheduler-role
  • Condition: iam:PassedToService = scheduler.amazonaws.com
  • Where: infra/modules/core/iam.tf · Sid SchedulerRolePassRole (PR #154 commit b8152e2)
  • Without this grant, the very first schedule_next_refresh call errors with AccessDeniedException: iam:PassRole and the chain dies at iteration 0. This was the regression the dev instance surfaced.
