## [Unreleased]

### Added
- **Three-level model selection — task label, per-user default, org default (issue #165).** The inference model is now resolved **per run** from three levels, the higher superseding the lower: a `model:<value>` issue label, the buyer's own default in `infra/user-pool/`, and the deployment default (`var.opencode_model`). The credential resolves on its own axis and travels with the user — per-user credential → org credential — so a buyer with their own key and no model override runs the **org default model on their own key**. New `lambda/model_select.py` holds the resolution; `lambda/bot_pool.py::get_opencode_profile` reads the per-user config. A local LLM keeps its current top precedence and the chain does not apply when one is configured. The binding rule: **a credential is used only with a model whose provider matches the credential's provider**, and a mismatch fails the webhook fast (HTTP 422, before any EC2 instance is launched) rather than sending a key to the wrong provider. The `model:` label resolves in two steps — an operator-registered alias (`opencode_model_profiles`, the `SPOT_INSTANCE_TYPES_JSON` precedent for JSON env vars), else a raw `<provider>/<model>` whose provider is on the operator's approved-provider list (`opencode_allowed_providers`); anything else is ignored with a warning naming the rejected value, and several `model:` labels resolve deterministically (alphabetically first that resolves). Raw strings are restricted because the run's credential rides along with the model — a labeler must not be able to point a run at an arbitrary endpoint. An operator-registered alias may use the org credential (the operator chose what it points at); a **raw** label may **not** — the org's shared key is never reachable from a raw label, so a raw label requires a per-user credential. `infra/user-pool/` gains `opencode_model` / `opencode_api_key` / `opencode_api_key_provider` / `opencode_base_url` / `opencode_base_url_allow_private_cidrs`, landing in the env-independent `/blitzlog/users/<login>/opencode/{model,api-key,provider,base-url}` namespace. The credential is a SecureString and **the Lambda never holds key material**: the user-data renders the resolved path (`OPENCODE_API_KEY_SSM_PARAM`) and the EC2 host reads `$OPENCODE_API_KEY_SSM_PARAM` — server-derived, never user-supplied text, so there is no injection surface; the org path remains the default. The container renders `options.baseURL` + an explicit `models` map when the resolved profile carries a base URL — without the map opencode emits `Model not found: <provider>/<id>` for a custom provider even when the endpoint is reachable — and the assisted-mode cloud fallback uses the same writer so it picks up the resolved credential. Label values are untrusted input that land inside the EC2 user-data bash script, so both the model string and the base URL go through strict allowlist validators that reject shell- and JSON-significant characters. `AGENTS.md` now forbids agents from applying `model:*` labels as well: a model label decides which provider a run's credential authenticates to, and the blast radius of that decision is a credential. 103 new tests across `tests/test_model_select.py`, `tests/test_llm_guard.py`, `tests/test_entrypoint_model_config.py`, `tests/test_bot_pool.py`, `tests/test_handler.py` and `tests/test_terraform_env_isolation.py`. Known limitations: the per-profile org credential (one org credential for now), per-repo model defaults, and automatic model fallback chains are follow-ups; the Alicloud tree keeps the org-default model and its existing KMS secret — the three-level selection ships on the AWS path only.
- **Scrummaster AMI baked in CI, in parallel with the agent AMI (epic #134).** New `scrummaster-packer` job in `release.yml` runs `infra/aws/packer/scrummaster-zeroclaw-docker-ubuntu.pkr.hcl` concurrently with the `release` job instead of after it, and publishes the AMI id to `/blitzlog/<env>/agent-ami-id-zeroclaw-docker-ubuntu` — the same env-scoped shape as the agent AMI. The ref-gate logic (issue #131: which refs qualify as a canonical release) was extracted from `release.yml`'s Detect step into a composite action at `.github/actions/ref-gate/action.yml`, which emits `mode` / `pr_number` / `blitzlog_env`. Both jobs call it, so the two bakes can never be published under different environments; the Detect step re-binds the action's outputs onto the keys its 48 existing `steps.detect.outputs.*` references already use, and still computes the version bump with git-cliff. `deploy` now declares `needs: [release, scrummaster-packer]` so a plan cannot read a missing AMI parameter once `enable_scrummaster` is on. `infra/aws/bootstrap/packer-role.tf` gains the SSM grant the OIDC post-processor needs, and drops the dead `workflow_path = ".github/workflows/packer-build.yml"` local (that file has never existed; the trust policy matches the OIDC `sub` claim instead).
- **Scrummaster renamed and env-scoped (epic #134).** `scrummaster-zeroclaw-ubuntu.pkr.hcl` → `scrummaster-zeroclaw-docker-ubuntu.pkr.hcl` and `scripts-scrummaster-ubuntu/` → `scripts-scrummaster-docker-ubuntu/`, matching the agent's `agent-docker-ubuntu` convention. The template gains `variable "environment"`, an env-scoped `ami_name`, and an `Environment` tag. The Terraform resources in `infra/aws/modules/core/scrummaster.tf` are now `blitzlog-${var.environment}-scrummaster-{role,ssm-read,profile,sg,eip}` with `Environment` tags — reversing the earlier env-independent decision, so `dev` and `prod` each get their own host, IAM objects and AMI with no collision, uniformly matching the rest of the core module. Both `infra/aws/dev/` and `infra/aws/prod/` now wire the four flags, both defaulting `false`. Two pre-existing bugs fixed along the way: the Packer template referenced `${path.root}/../scrummaster/systemd/`, which the fold into `modules/core` had made non-existent (the bake would have failed at its first provisioner), and the AMI precondition's error message still named the old un-scoped SSM path. Renaming changes `iam_instance_profile`, which forces replacement of the running instance; because it carries `disable_api_termination = true`, that is a deliberate operator procedure, documented as a runbook at the foot of `scrummaster.tf`. 25 new tests across `tests/test_scrummaster_infra.py` and `tests/test_release_workflow.py`.
- **Scrummaster folded into the AWS core module (epic #134).** The always-on Scrummaster advisor host moved from the standalone stack `infra/scrummaster/` into `infra/aws/modules/core/scrummaster.tf`, with its assets under `infra/aws/modules/core/scrummaster/` (`user-data.sh`, `systemd/`, `tests/smoketest.sh`, `README.md`). A separate stack meant a second provider download, a second lock file, a second variable set, and a hand-run `terraform apply` that CI never touched; folding it in makes "apply the whole system" a single CI-owned plan/apply. All eight resources sit behind `count = var.enable_scrummaster ? 1 : 0` — the same optional-feature idiom `alerting.tf` / `ec2.tf` / `storage.tf` already use — and the flag defaults to `false` because enabling it needs a Packer bake to have published `/blitzlog/scrummaster/agent-ami-id-zeroclaw-ubuntu` first and nothing in CI builds that AMI yet. Four new core variables (`enable_scrummaster`, `zeroclaw_image_tag`, `ssh_key_name`, `enable_scrummaster_eip`) and four `try()`-guarded outputs. The resources keep their env-independent names (`blitzlog-scrummaster-*`, no `${var.environment}` infix) like `/blitzlog/users/*` and the shared S3 buckets: renaming them changes `iam_instance_profile` and would force replacement of an instance carrying `disable_api_termination = true`. Because the names are env-independent, `dev` is the only env wired to enable it — `infra/aws/prod/` deliberately is not. `prevent_destroy` on the instance now also blocks destroying the whole dev/prod stack; accepted deliberately, `dev` exists to be broken. Guarded by 9 new tests in `tests/test_scrummaster_infra.py::TestScrummasterInCoreModule`.
- **Alicloud Terraform module tree with per-env provider dispatch (issue #126).** New `infra/alicloud/{modules/core,dev,prod,bootstrap}/` mirrors the AWS tree 1-to-1 (Function Compute + ECS + RAM + API Gateway + OSS + MNS + KMS analogues). The release workflow reads `vars.BLITZLOG_PROVIDER` (default `aws`) and switches the working-directory + backend (S3 vs OSS) + tfvars file accordingly. Per-provider tfvars live at `infra/<provider>/<env>/<provider>.tfvars` (operator-copied from the `.example` file). The dispatch is regression-guarded by `tests/test_terraform_env_isolation.py::TestAlicloudProviderDispatch`. Known limitations: no EventBridge Scheduler equivalent of #145's token-refresh chain on the Alicloud path (1 h token cap is operationally visible), no Aliyun image-builder yet (Packer is AWS-only — the release workflow fails fast when `BLITZLOG_PROVIDER=alicloud` until Phase 5). Closes #126.
- **User-data scripts split (issue #126 follow-on).** `lambda/scripts/{_common,autonomous,assisted}.py` moved into `lambda/scripts/aws/`; new `lambda/scripts/alicloud/{_common,autonomous,assisted}.py` provides the OSS + KMS variants. The `BLITZLOG_PROVIDER` env var dispatches to the right cloud's user-data builder via `lambda/scripts/__init__.py`. The Packer image is still AWS-only; the Alicloud user-data installs `ossutil` + `aliyun` CLI on first boot (~10s) and inlines a `blitzlog_oss_*` bash library (parallel to the Packer-baked `blitzlog_s3_*` on the AWS path). The Aliyun IMDS at 100.100.100.200 replaces AWS IMDSv2; `aliyun kms GetSecretValue` replaces `aws ssm get-parameter`. The bucket env-var names are `OSS_LOGS_BUCKET` / `OSS_LOG_PREFIX` (vs the AWS-side `S3_*` prefix). `lambda/handler.py:55-56` now imports from the `scripts` package instead of the flat `scripts.assisted` / `scripts.autonomous` modules. Regression-guarded by `tests/test_scripts_dispatch.py` + `tests/test_scripts_autonomous_alicloud.py` + `tests/test_scripts_assisted_alicloud.py`. Known limitations: the watchdog's log upload is still hard-coded to the AWS-side `blitzlog_s3_*` library (Packer-baked at `/usr/local/bin/blitzlog_uploader.sh`); on the Alicloud path the upload fails silently (`|| true` swallow) — the MNS DLQ + FC dead-letter config catch the failure. A per-cloud Packer image is Phase 5 follow-up.
- **Alicloud provider currency + deprecation cleanup (#155 follow-up).** Bumped every Alicloud stack from `aliyun/alicloud ~> 1.0` (locked at 1.294.0) to `~> 2.0` (v2.0.0 shipped 2026-10-12; breaking changes don't touch any resource blitzlog uses). Fixed the CI-breaking hard error `Call to function "filemd5" failed: lambda/requirements.txt: no such file or directory` by routing the requirements file through a new `var.lambda_requirements` (default `requirements-alicloud.txt`, mirroring the AWS shape). Migrated three resource-level deprecations: `alicloud_fc_service` + `alicloud_fc_function` → `alicloud_fcv3_function` (FCV3, `fc:2023-03-30` API — the function zip is now uploaded to the shared agent-logs OSS bucket via `alicloud_oss_bucket_object.fc_code` and the FC execution role has an `oss:GetObject` grant scoped to that key); `alicloud_mns_queue` → `alicloud_message_service_queue`. Fixed field-level deprecations: `alicloud_security_group.name` → `security_group_name`, `alicloud_kms_key.key_state` → `status`, `alicloud_ram_role.name` → `role_name` and all `.name` attribute references → `.role_name`, `alicloud_oss_bucket.acl` → `alicloud_oss_bucket_acl`. `infra/alicloud/{dev,prod}/main.tf` now declare `required_providers { alicloud = { source = "aliyun/alicloud" } }` so the root's `provider "alicloud" {}` block resolves to the correct provider source (previously the implicit `hashicorp/alicloud` was being pulled in alongside the real one — a dead 200 MB provider binary per deploy). Terraform binary bumped 1.9.8 → 1.16.6 in `mise.toml`, `lint.yml`, `release.yml`, `terraform-apply-dev.yml` (provider 2.0 framework needs ≥1.10); the stale mise `tf-plan` / `tf-apply` tasks (still pointing at the now-empty `dir = "infra"`) repointed to `infra/aws/dev`. Regression-guarded by 11 new tests in `tests/test_terraform_env_isolation.py::TestAlicloudProviderDispatch` covering the provider pin, the missing-`required_providers` bug, the legacy resource types, the field renames, the OSS code-delivery shape, the `lambda_requirements` variable, the FCV3 wiring, the FC code-grant, the Terraform version pin, and the mise task repointing. Follow-up: the `hashicorp/aws ~> 5.0` pin (AWS stack) is left alone — its major-version bump deserves its own issue + PR.

### Changed
- **Per-cloud Terraform tree layout (issue #126).** All AWS-only Terraform paths moved from `infra/{modules,dev,prod,bootstrap,packer}/` to `infra/aws/{modules/core,dev,prod,bootstrap,packer}/`. Each per-cloud tree is self-contained: there is no shared cross-cloud path. `infra/user-pool/` stays at the top level for now (Phase 5 follow-up moves it to `infra/{aws,alicloud}/user-pool/`).
- **Pre-built agent AMI with baked-in Docker image (Amazon Linux 2023 + Ubuntu 24.04).** Two minimal arm64 AMIs per env ship with `dockerd` + awscli + git + jq + the host-side watchdog (`/usr/local/bin/watchdog.sh`) + a gzipped `ghcr.io/great-wall-connect/blitzlog-agent` container image tarball at `/opt/blitzlog/images/`. The container has zero AWS credentials; the host user-data does all SSM/S3 work and passes results via env vars + mounted files. Cold start drops from ~3-5 min (today) to ~22-60s. See `docs/DOCKER.md` for the operator-facing doc. Closes #55.
- **Per-run EC2 Tailscale enrollment for local-LLM transport.** New `tailscale_auth_key` user-pool variable + SSM param at `/blitzlog/users/<login>/local-llm/tailscale-auth-key` (SecureString). When set, the bootstrap installs `tailscale` (AL2023 repo), runs `tailscale up --authkey=... --hostname=blitzlog-agent-<issue>-<ts> --ephemeral --accept-routes=false`, and waits for `BackendState=Running` before the existing `preflight_local_llm()` probe. Ephemeral nodes auto-remove when the spot instance terminates — no manual cleanup. The auth key should be generated at https://login.tailscale.com/admin/settings/keys with `Ephemeral: enabled`, `Reusable: enabled`, `Tags: tag:blitzlog-agent`. The user's Tailnet ACL must grant `tag:blitzlog-agent` access to the LLM endpoint's IP (out of scope for blitzlog to manage). README "Transports → Tailscale" section documents the recommended flags and ACL requirement. This makes the local-LLM feature verifiable end-to-end without provisioning a static subnet router, exit node, or VPN endpoint in the dev VPC.

### Changed
- **Per-user bot pool and local LLM config are now env-independent (refines #50).** The `infra/user-pool/` module is back at its original standalone location (out of `infra/modules/core/user-pool/`) and no longer takes an `environment` variable. Bot tokens and per-user local LLM config live under `/blitzlog/users/<login>/...` (no env prefix), so a user configures their pool once and both prod and dev Lambdas read from the same namespace. The Lambda reads these via a new `BOT_POOL_SSM_PATH = "/blitzlog/users"` constant, distinct from the env-scoped `SSM_PATH` used for env-specific resources (GitHub App creds, ephemeral tokens, STT config, opencode api key). The IAM policies in `infra/modules/core/iam.tf` reflect the new split: bot-pool and local-LLM grants use the literal `/blitzlog/users/*` ARN; ephemeral-token grants remain env-scoped under `${local.ssm_ephemeral_root}/*`.
- **Route agents to user-owned local LLMs (closes #24).** Per-user SSM params (`local_llm_endpoint`, `local_llm_model`, `local_llm_api_key`, `local_llm_endpoint_allow_private_cidrs`, `local_llm_fallback`) under `/blitzlog/users/<login>/local-llm/`. When configured, the bootstrap writes a `local` provider block in `opencode.json` and switches `OPENCODE_MODEL=local/<model-id>`; the cloud provider block is omitted and `OPENCODE_API_KEY` is not exported to the agent's environment (read on demand only for the assisted-mode cloud-fallback path). Endpoint safety guard hard-rejects public IPs and requires `local_llm_endpoint_allow_private_cidrs=true` for RFC1918/ULA/Tailscale CGNAT. Preflight probe runs 10×30s before opencode launches. Autonomous mode aborts on exhaustion; assisted mode prompts the user on Telegram with `[Retry]/[Abort]` (plus `[Use cloud fallback]` when `local_llm_fallback=cloud`) and waits up to 10 minutes for a reply. README documents three always-on transports (Tailscale, WireGuard, AWS Client VPN).
- `opencode serve` now binds to `--hostname 127.0.0.1 --port 4096` (was `--port 4096`).
- Defensive `unset OPENCODE_API_KEY HTTPS_PROXY HTTP_PROXY` at the top of every bootstrap.
- **Bootstrap stack for shared S3 buckets (refines #50).** The `agent_logs` and `stt_models` S3 buckets are now owned by a separate one-time stack at `infra/bootstrap/` instead of being created by every per-env stack. Each env (`infra/prod/`, `infra/dev/`, ...) references the same buckets via `data "aws_s3_bucket"` resources — so a dev `terraform apply` no longer fails with `BucketAlreadyOwnedByYou`, and encryption / versioning / lifecycle / public-access-block configuration is centralized in the bootstrap stack. State migration for the existing prod deploy is documented in the README's "Migrating S3 buckets out of the prod stack into the bootstrap stack" section.
- **Dev/prod segregation (closes #50).** Blitzlog now runs in two isolated environments inside the same AWS account. `infra/prod/` and `infra/dev/` are thin Terraform wrappers that call `infra/modules/core/` with `environment = "prod"` or `"dev"`. Each env has its own state file (`prod/blitzlog.tfstate` vs `dev/blitzlog.tfstate`), its own resource names (`blitzlog-prod-handler` vs `blitzlog-dev-handler`, etc.), its own SSM namespace (`/blitzlog/prod/*` vs `/blitzlog/dev/*`), and its own IAM roles scoped to its own prefix — so the prod Lambda role literally cannot read `/blitzlog/dev/*` and vice versa. Per-user bot pools and per-user local LLM config are explicitly NOT env-namespaced (see the `Changed` entry above). The Lambda reads `BLITZLOG_ENV` from its env vars (set by Terraform from `var.environment`) and templates all env-scoped SSM paths under `/blitzlog/<env>/`. The README's new "Environments (prod / dev)" section documents the workflow.
- Per-user bot pool module (`infra/user-pool/`) uses local Terraform state instead of a shared S3 backend, eliminating S3 state-key collisions across users and the central DynamoDB lock-table requirement. `terraform.tfvars` remains the per-user source of truth; the local `terraform.tfstate` is a regenerable cache of resolved SSM ARNs.
- **Bump agent AMI base from Ubuntu 24.04 LTS to Ubuntu 26.04 LTS (resolute).** `infra/packer/agent-docker-ubuntu.pkr.hcl` source-AMI filter switched from `ubuntu-noble-24.04-arm64-server-*` to `ubuntu-resolute-26.04-arm64-server-*`. The 24.04 Packer provisioner scripts updated to use the `resolute` Docker apt repo. `lambda/ec2.py:get_latest_ubuntu_ami()` now reads the `/aws/service/canonical/ubuntu/server/26.04/stable/current/arm64/hvm/ebs-gp3/ami-id` SSM parameter (verified to exist in `ap-east-1`).
- **Bootstrap now `docker run`s the pre-baked agent image instead of running opencode on the host.** The previous bootstrap ran `opencode serve` and `npx @grinev/opencode-telegram-bot@latest start` directly on the EC2 host, but those binaries only exist inside the `blitzlog-agent` Docker image (baked into the AMI by Packer). The new bootstrap loads `/opt/blitzlog/images/blitzlog-agent.tar.gz` into dockerd and runs `docker run -d --name blitzlog-agent` with the right env vars (`MODE`, `ISSUE_NUMBER`, `REPO`, `OPENCODE_*`, `TELEGRAM_*`) and volume mounts (`/opt/whisper-stt/models`, `/root/.config/opencode`, `/workspace`). The container's entrypoint runs `opencode serve` and the Telegram bot internally. The host-side shutdown helper still handles log uploads, session archival to S3, and instance termination (since the container has no AWS credentials).
- **Add `gh` to the `blitzlog-agent` Docker image runtime stage.** The bootstrap used `gh issue view` to fetch the issue title for the Telegram banner. With `gh` now in the container image, the host bootstrap no longer needs it.
- **Drop `git` and `gh` from the Packer AMI `01-system.sh`.** The host no longer needs git (the container clones in `entrypoint.sh`) or gh (the container has it baked in).
- **Delete `_configure_git_script()` and `_install_system_packages_script()` from `_common.py`.** Pure dead-code removal: both were AL2023/Docker-era holdovers. The first wrote host-side `git config` (no longer needed — container handles its own git). The second was an AL2023-only `dnf install gh` block.
- **Remove `_clone_repo_script()` and its calls.** Superseded by Item 7 — the container clones via `entrypoint.sh`, so the host no longer needs to clone.
- **Remove the `gh issue view` line in `assisted.py`.** The issue title is no longer in the Telegram banner (cosmetic regression: banner shows `Issue #2` instead of `Issue #2: <title>`). `gh` is available in the container if future bootstrap code wants to fetch it.

The `agent_os_family` Terraform variable and the `AGENT_OS_FAMILY` lambda env var are removed. `lambda/ec2.py:get_agent_ami()` is now Ubuntu-only and reads `/blitzlog/<env>/agent-ami-id-docker-ubuntu` directly. ### Fixed
- **The local-LLM bootstrap aborted before the agent started.** The `/etc/blitzlog.env` heredoc expanded `$OPENCODE_API_KEY` under `set -u` on a run with a local LLM configured — and the cloud key is deliberately NOT fetched in that case, so the variable was unset and the bootstrap died with `unbound variable` before the watchdog ever started. The same unbound-variable hazard in the assisted mode's `api_key_prefix` diagnostic log line is fixed the same way (`printf '%.8s'` with a `:-` default). Found while implementing issue #165, whose acceptance criteria require the local LLM to stay on top of the new resolution chain — a path that could not be reached before.
- **The instance metadata service is now unreachable from the agent container.** The container runs as root on the docker bridge and could reach `169.254.169.254`, assume the EC2 instance role, and read any per-user credential the role can see — which issue #165 widens to `/blitzlog/users/*/opencode/*`. The watchdog now drops IMDS traffic from the container's network (the `DOCKER-USER` chain only sees forwarded container traffic, so the host's own IMDS access is untouched) and passes `AWS_EC2_METADATA_DISABLED=true` to the container as a second layer. The rule is best-effort by design: if `iptables` is unavailable the run continues and logs a warning. Issue #164 (non-root container, dropped capabilities, read-only rootfs) is the real containment mechanism.
- **Make `local-exec` use Python 3.12 so the lambda build matches the runtime.** `infra/modules/core/lambda.tf` `null_resource.lambda_build`'s `local-exec` used bare `python3 -m venv`, which resolves to `python3.14` on Ubuntu Desktop (where `python3` is 3.14). The resulting `infra/modules/core/build/` contained `_cffi_backend.cpython-314-x86_64-linux-gnu.so` wheels from `cryptography`; the Python 3.12 lambda runtime couldn't import them, so `cryptography` failed to load and PyJWT raised `NotImplementedError: Algorithm 'RS256' could not be found` on the first GitHub App auth path. The local-exec now resolves Python 3.12 explicitly — `command -v python3.12` first (so macOS hosts Just Work), then falls back to the mise install dir (`~/.local/share/mise/installs/python/3.12.*/bin/python3`, since `mise.toml` pins `python = "3.12"`), and fails loudly if neither exists. The lambda runtime stays `python3.12` (the highest Python version supported by Lambda in `ap-east-1`; `python3.14` is not supported there).
- **Restore `git clone ... /workspace/repo` in the bootstrap.** The lambda user-data generated by `lambda/scripts/assisted.py` and `lambda/scripts/autonomous.py` ran `cd /workspace/repo` after the session-restore step without ever cloning the repo, crashing with `cd: /workspace/repo: No such file or directory` at line 401 of the rendered script. The clone block was lost during the handler.py → focused-modules split (PR #56). Restored as `_clone_repo_script(repo)` helper in `lambda/scripts/_common.py`; called from both modes right after `_configure_git_script()` and before `_session_restore_script()`. Regression test `TestCloneRepoScript` in `tests/test_scripts_common.py`.
- **Use Python f-string `{repo}` instead of Packer template `${{REPO}}` in `_clone_repo_script`.** The bootstrap never goes through Packer template substitution — the lambda renders the script and ships it directly to bash. The first fix used `${{REPO}}` (Packer syntax), which bash parsed as a bad substitution at line 75 (`https://github.com/${{REPO}}}.git: bad substitution`). Switched to f-string substitution so the resolved URL is baked into the bootstrap at lambda render time.
